## 一、專案背景與目標

市集與商圈舉辦活動時，常靠紙本集章卡引導人潮走訪各攤位／景點，但紙本**無法統計、易偽造、獎項核銷混亂，也拿不到參與數據**。

本專案將現有的前端原型（`加蚋仔集章地圖`：互動地圖、集章卡、掃碼、獎項兌換）升級為一套**跑在 LINE 上的線上集章系統**：

- 透過 **LINE LIFF** 免下載 App、以使用者既有 LINE 身分即可參與
- 後端持久化資料，提供**防作弊**與**獎項核銷**機制
- 協助市集／商圈**優化走訪動線與體驗流程**，並沉澱可分析的參與數據

**產品定位**：多租戶（多商圈／多活動）集章平台。架構一次設計到位，但 **v1 開發先聚焦前台使用者端 LIFF App**；營運後台與數據分析納入架構藍圖，於後續階段實作。

## 二、技術架構

**單一 Nuxt 3 全端專案**（Nuxt 本身即 Vue 框架，前後端共用一個 codebase）：

| 層 | 技術 | 說明 |
|----|------|------|
| 前端 | Nuxt 3 + Vue 3 SFC + Tailwind v4 | 頁面／元件，沿用原型 UI |
| 狀態 | Pinia | 集章進度、使用者、活動資料 |
| 後端 API | Nuxt Nitro `server/api/*` | REST 端點，與前端同源免跨域 |
| 資料庫 | MongoDB（Atlas）+ Mongoose | 多租戶集合、索引、交易 |
| 身分 | LINE LIFF SDK + LINE Login | 取得 LINE 使用者身分、掃碼、分享 |
| 部署 | Node 主機（Cloud Run／Vercel／VPS）+ MongoDB Atlas | LIFF 必須 HTTPS |

**為什麼選單一 Nuxt 全端**：前後端同源、同一套型別、單一部署與網域，最省維運成本；Nitro server routes 足以承載本專案的 API 量與防作弊邏輯。

## 三、資料模型（MongoDB，多租戶設計）

以 `campaignId` / `tenantId` 貫穿各集合，確保不同商圈資料隔離。

| 集合 | 主要欄位 |
|------|----------|
| **Tenant**（商圈／市集擁有者） | `name`, `contact`, `liffId`, `lineChannelId`, `status` |
| **Campaign**（活動） | `tenantId`, `title`, `description`, `startAt`, `endAt`, `theme`, `mapConfig`, `status` |
| **Station**（集章點） | `campaignId`, `name`, `title`, `description`, `address`, `geo{lat,lng}`, `mapCoord{x,y}`, `imgUrl`, `type`, `specialty`, `qrSecret`, `order`, `noStamp` |
| **Reward**（獎項） | `campaignId`, `title`, `requirementCount`, `rewardName`, `iconType`, `stock`, `perUserLimit` |
| **User**（LINE 使用者） | `lineUserId`（唯一索引）, `displayName`, `pictureUrl`, `createdAt` |
| **StampRecord**（集章紀錄） | `userId`, `campaignId`, `stationId`, `collectedAt`, `verifiedGeo`；`(userId, stationId)` 唯一索引防重複 |
| **Redemption**（獎項核銷） | `userId`, `campaignId`, `rewardId`, `code`, `status`(`pending`/`redeemed`), `claimedAt`, `redeemedAt`, `redeemedBy` |

> `Station`／`Reward` 欄位對齊現有原型資料結構，原型的 10 個集章點與 3 個獎項門檻（1／3／6）可直接作為加蚋仔商圈的種子資料匯入。

## 四、核心流程

1. **登入**：LIFF init → `liff.login()` → 取得 `idToken` → 後端向 LINE 驗證 → upsert User → 發放 session（HttpOnly Cookie／JWT）。
2. **載入活動**：依 `campaignId` 回傳集章點、獎項門檻、使用者已集章／已兌換狀態 → 渲染地圖、集章卡、進度條。
3. **掃碼集章**：掃 QR → 後端驗證（QR 簽章有效未過期 + GPS 在半徑內 + 活動進行中 + 未重複）→ 寫入 StampRecord → 回傳更新後進度。
4. **獎項兌換 + 核銷**：達門檻 → 領取獎項 → 產生核銷碼／QR → 商家端掃碼或輸入碼 → 後端驗證、`status` 改 `redeemed`、扣庫存、記錄核銷人／時間，防重複兌換。

## 五、防作弊機制

- **QR 簽章**：每個集章點 QR 內含 `stationId + timestamp + nonce`，以 `qrSecret` 做 HMAC 簽章，後端驗章並設 TTL。
- **GPS 地理圍籬**：以 Haversine 計算使用者座標與 `station.geo` 距離，超過半徑（例如 100–200m）拒絕。
- **伺服器端把關**：idToken 驗證、`(userId, stationId)` 唯一索引去重、API 速率限制、活動時間窗檢查。
- **v1 策略**：採「**半靜態簽章 QR（貼紙／立牌）+ GPS**」，低成本、免現場設備，已能擋掉遠端代掃；動態輪替 QR 列為未來進階。

## 十、驗證方式（End-to-End）

- **LIFF 登入**：於 LINE App 開啟 LIFF URL，確認取得使用者身分並建立 session。
- **集章流程**：實地或模擬 GPS，掃描集章點 QR，確認：合法碼可集章、過期／偽造碼被拒、跨半徑被拒、重複掃不重複計。
- **獎項核銷**：集滿門檻領獎 → 產生核銷碼 → 商家端核銷 → 確認狀態變更、扣庫存、無法重複兌換。
- **資料一致性**：MongoDB 檢查 StampRecord 唯一索引、Redemption 狀態機正確。
- **裝置相容**：iOS／Android LINE 內建瀏覽器實測相機權限與掃碼。
